# 架构与产品合同窄复核关闭记录

## 结论与范围

此前 CR-A01（基线失效发布行为）、CR-A02（21 子功能缺逐项决定）、CR-A05（16 资源缺可执行的扩展合同设计）和 CR-A06（跨市场单位范围）现已在规格或合同设计层闭环。公共合同仍为 **31 个操作、80 张 SQL 表**，与 v3.1 基线对应文件字节一致；本轮没有把设计提案记作生产功能。

新扩展卡最终冻结为 **16 张资源卡、41 个拟新增操作、40 个提案类型、27 个持久化或注册定义、14 个拟新增 SQL 表、24 个重点已有字段绑定**。14 表中 `access.account_grant` 是条件项：已有持久授权系统可由端口绑定，不要求重复建表。27 项还包括 manifest 数据集、既有 JSON 列的严格 payload 注册与明确的未来 schema 迁移，不是 27 张新表。

输入资源、子能力、数据作业共 **21 / 16 / 20** 项均生成独立映射。主审最新 `root_final.json` 为 **137 决定，475/475 实质单元**，未发现漏项或重复分配。这个计数只对应主审负责的五个文件，不冒充整个 11 卷总量。

精确哈希、计数及检查结果见 `cold_arch_root_closure.json`；复跑脚本是 `check_product_closure.py`。本轮检查只覆盖这些已有发现及其直接合同边界，不重新评价论文和交易制度原文。

## 真实字段和能力边界

1. `execution.account_head.current_sequence` 是账户版本来源；不存在名为 `execution.account` 的表，也不存在已定义的账户 owner 列。账户授权需真实外部持久来源或明确的新授权表。
2. 分录使用 `execution.journal_entry` 与 `execution.journal_line`，没有 `execution.ledger_entry`。制度和费用的当前方案是有版本的数据集/合同，不冒充已有 `execution.ruleset` 或 `execution.cost_profile` 表。
3. `execution.order_reservation` 是资源预留，不是完整 OMS。订单页需要按注册的执行事件状态机生成投影；不完整历史显示 partial/unknown。绩效投影从同一 Journal 和估值输入计算，不另写余额账。
4. 席位身份的真实字段为 `seat_id`、`seat_version`；榜单为 `report_revision_id`。匿名机构或报告局部标签没有全局身份时保留 null 与局部引用，不发明 UUID 合并成“已确认营业部”。
5. `ops.job_run` 保存参数 hash，没有完整运行参数；D25 明确保存可恢复参数产物。公共 `JobRun` 没有结果文件字段，因此计划提案、筛选、导出分别通过类型化结果查询取得产物；`JobReceipt.resource_id` 和 `poll_operation_id` 有明确绑定。
6. `ui.annotation` 与 `ui.workspace_layout` 是当前状态。画线告警引用历史版本需要 D23 的不可变 revision；迁移只能保存可取得的历史，不能把今天的图形伪装成旧版。绘图、笔记、复盘仍沿用现有 drawing/note/review 枚举。
7. 当前 `ExperimentRequest` 只有六个字段，ReplaySpec 不能偷偷塞入 3.0.0 请求。当前 `EvaluationContext` 训练起止强制非空，no_fit 需要显式后续 schema/SQL 迁移；未完成时返回不支持的上下文形状，不能伪造训练窗。
8. 当前 `UpdateNotification` 只允许四种事件。SSE 初期只是这四种事件的可恢复传输；告警、workspace、job 的新增公开事件必须完成新版本与客户端兼容，outbox 能存内部事件不代表当前 DTO 自动接受。
9. 非 READY manifest 可以没有内容 hash，不能强行序列化为要求非空 hash 的 `SnapshotRef`。新的 DatasetStatus 投影把状态和可空 `ready_snapshot` 分开。
10. 大部分新增对象只是数据集与投影，物理上仍适配 single PostgreSQL + immutable local files + transactional outbox。没有因此重新引入必需 NATS、独立目录库或多个经济账本。

字段检查是对实际 DDL 的静态核对；不宣称这些提案已生成可运行迁移，也没有对目标机器做吞吐或内存测试。

## 运行职责映射

| 上传入口 | 新架构职责 | 执行与资源边界 |
| --- | --- | --- |
| pulse-collector | 摄取、规范化、来源健康 | 可在一个受限异步进程运行；来源限速和 7×24 消息窗口保留 |
| pulse-stream | 低延迟分析、计划重评估、告警求值 | 队列优先级与批研究隔离；不要求另建数据库 |
| pulse-worker | 特征/排序批任务、唯一账本仿真、对账、发布 | 按作业分类和资源预算运行；发布只提交完整依赖 |
| pulse-api | 产品 API、更新流、静态前端 | 读冻结产物和授权投影，不在 GET 里抓外部源 |
| pulse-watchdog | 服务管理、心跳、新鲜度和磁盘监督 | 位于运维职责；可由原生服务管理器加轻量探针实现，不要求常驻交易 Agent |
| pulse-lab（原文另列） | 离线研究执行配置 | 可在 PC 或独立研究进程运行；通过输入/输出 manifest 导入，不能直接改服务器事实账本 |

这保留了原五个入口的责任，同时允许小机合并轻任务。表中的六行包含原文另列的研究配置，不是“必须六个常驻 Python 进程”。

## 验收限制

本次完成的是设计与静态绑定闭环。新增应用操作仍须注册公开合同、生成客户端、实施持久对象与应用服务，并通过各卡专属验收。现有公共合同和 SQL 没有因为新增设计而修改。GC/publish 的锁与 pin 协议已在主规范明确，但并发实现仍需按其特定竞态场景验证，不能由文档文字直接推定实现正确。

对这批卡片另请独立审查员做 PEX05/06/12/14/15/16 的窄交叉检查；其发现另存 `product_extension_cross_review.md`，不覆盖历史审查记录。
