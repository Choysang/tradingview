# 08 · 并行开发计划

> 本卷回答：多个编码智能体怎样同时开工而不互相踩踏、先做什么后做什么、每一步怎样算完成、什么时候从旧系统切换到新系统。
> 适用对象：负责编排的主智能体，以及领取任务卡的各执行智能体。

## 1. 开发方式

1. **契约先行。** 任何跨包的东西（数据集、事件、接口、策略规格、交易对象）先在 `contracts/` 定稿，再并行实现。契约改动单独提交，由契约负责人合并。
2. **包边界就是所有权边界。** 一条车道拥有一组路径；一张任务卡只改自己车道的路径。需要别的车道改动时，提交一张给对方的任务卡，不直接改。
3. **验收测试就是规格。** 每张任务卡先落地失败的验收测试，再写实现。本规格 07 卷第 9 节的 25 条标准用例、04 卷的校验规则、01 卷第 6 节的继承规则，都以测试的形式先进入仓库。
4. **新代码不读旧代码。** `rebuild` 分支的工作树里没有旧代码。需要旧系统的行为作参照时，以本规格的文字与标准用例为准；规格没写清楚的，提问并补规格，不去翻旧实现。唯一的例外是迁移车道（L12）：它读取旧数据与旧产物，把旧脚本当黑盒运行来导出清单与标准样例，但不把旧实现搬进新代码。
5. **一张卡，一个智能体，一个工作树。** 完成后由独立的审查智能体在没有上下文的情况下审查差异，再合并。
6. **主智能体只做三件事**：拆卡与排序、裁决契约与口径、集成与验收。实现交给执行智能体。
7. **重任务串行。** 回测电池、全量回填、训练一次只跑一个，沿用排他队列。

每个里程碑的“完成标准”都是可执行的检查。

### M5 并行运行

新系统在服务器上与旧系统并行运行，旧系统是记录方。

| 检查 | 标准 |
|---|---|
| 连续交易日 | 不少于 10 个交易日全链路无丢失（采集、日更、信号、榜单、纸面、对账） |
| 数据 | 新旧日线逐日收益一致率不低于 99.9%，差异可解释 |
| 榜单 | 以同一融合分为输入，新旧主书逐日持仓一致或差异可归因 |
| 健康 | 至少演练一次源中断与一次进程被杀，系统自动恢复且有告警 |
| 资源 | 五个进程合计内存峰值不超过 3.5 GB；磁盘占用符合 04 卷第 12 节 |
| 主干打分 | 融合分要么已移植并通过验收，要么旧打分流程被明确保留为外部产出方并有监控（当日打分缺失即告警、推荐榜标注“主干缺失”） |

### M6 切换与扩展

切换：新系统成为记录方，旧系统停止写入并整体归档；唯一的例外是尚未移植完成时保留的旧打分流程。前向记录在切换日标注“记录方变更”，两段记录都保留。

之后按价值排序扩展：其余官方与通讯社消息源；其他社区平台的热度与观点对账；其余资金面数据（两融、大宗、增减持、回购、调研、ETF 份额）；发现闭环的自动抓取与假设卡；论文方法的候选接入（06 卷第 11 节）；图表的画线告警、回放、多图联动；无代码策略搭建。

## 4. 任务卡

```text
编号与标题
车道与所有权        可以修改的路径（白名单）；只读可见的路径
目标                一句话
规格引用            本规格的卷与节
契约                涉及的模型；是否需要契约变更（需要则先提契约卡）
验收测试            先落地的失败测试清单；通过即完成
不做什么            明确排除的范围
口径                已拍板的阈值与规则，照抄，不得改动
交付说明            完成后填写：做了什么、没做什么、未验证的是什么
```

规则：

- 卡片的规模以“一个智能体一次会话能完成并自测”为上限；超过就拆。
- 卡片之间的先后只通过“依赖的测试已变绿”表达。
- 执行智能体发现规格有歧义或与事实冲突时，停下来提问并附证据，不自行改口径。
- 审查智能体冷启动，只看卡片、规格引用与差异；严重问题必须修复后再合并。

## 5. 所有权与冲突

- 两个智能体不得同时修改同一文件。所有权清单在各包的 `AGENTS.md` 里，由持续集成检查“差异是否越界”。
- `contracts/` 只有 L0 的负责人可以合并；其他车道提交变更请求。
- 共享的配置（规则表、费用表、新鲜度目标、晋升门槛）是数据，不是代码：改动走“拍板、登记、加测试锁定”的流程。
- 发现别的车道的缺陷：写一条带最小复现的缺陷卡给对方，不顺手修。

## 6. 质量门禁（每次合并前自动执行）

| 门禁 | 内容 |
|---|---|
| 格式与静态检查 | 格式化、静态检查、类型检查 |
| 导入边界 | 03 卷第 4 节的依赖方向；`kernel` 无 IO；业务代码里不得出现对证券代码前缀的判断 |
| 契约漂移 | 重新生成 OpenAPI、TypeScript、DDL、字段字典后与仓库一致 |
| 命名规范 | 规范表里不得出现无单位后缀的数值字段、不得出现“手、万元、亿元”口径 |
| 无前视 | 所有注册的特征、信号、策略自动跑截断测试 |
| 标准用例 | 07 卷第 9 节 |
| 禁止模式 | 裸 `except`；对空值填 0；无超时的网络调用；直接写最终文件名；会写入的读取接口；业务代码里的魔法常数（成本、阈值必须来自配置表） |
| 覆盖率 | 内核、仿真、账本、校验不低于 90%；其余不低于 80% |
| 性能预算 | 全市场一次特征计算、一次融合打分、一次三年组合回测各自的时间上限 |

“禁止模式”一栏逐条对应 01 卷里反复出现的缺陷类型。

## 7. 运维与部署

- 五个服务的定义、环境变量、计划任务全部在 `ops/`，部署脚本可重复执行。
- 部署前比对文件哈希、备份被替换的文件、部署后做健康检查；这些是现有手工流程里已验证的步骤，写成脚本。
- 密钥只存在于服务器的受限目录。
- 备份：状态库每日备份并做恢复演练；数据湖按清单增量同步到 PC。
- 服务器重启后五个服务自动拉起，采集器从游标续抓并触发缺口回补。

## 8. 已知风险与对策

| 风险 | 对策 |
|---|---|
| 云服务器 IP 被部分行情源拒绝或不稳定 | 每个数据需求至少两个源；PC 作为补抓节点；主源改为凭令牌访问的接口（10 卷 D03） |
| 服务器磁盘只有约 50 GB | 原始响应 90 天后转存；M1 必须交付转存与清单 |
| PC 常关机 | 生产链路不依赖 PC；需要重型环境的打分在晋升前导出为服务器可执行的形式 |
| 大模型费用与供应商变动 | 规则优先；网关统一预算熔断；模型标识与提示词版本钉死；供应商可替换 |
| 样本外证据积累慢 | 接受。界面如实显示证据等级；不为了让榜单好看而降低门槛 |
| 规则表里尚有待核条目 | M0 逐条核对官方原文；核不到的不设默认值 |
| 调研里的版本号、接口可用性多为二手信息 | 实现当天以官方发布页为准并锁定版本；接入每个源之前先做一次低频探测并留样 |

|---|---|
