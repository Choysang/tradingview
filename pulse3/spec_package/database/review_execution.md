# 统一执行参考实现的独立冷审

审查者：数据库与接口专项 Agent。日期：2026-11-10。

范围：`execution/unified_ledger.py`、`test_unified_ledger.py`、`golden_fixtures.json`，同时读取 `execution_standard.md` 确定已声明的原型边界。本审查没有修改执行专项文件。依据来自实际代码、运行输出和独立算术反例；不以“财务标准名称”代替行为验证。

## 结论

现有参考的复式金额、数量子账、交易应收应付、加权毛价成本、分红与外部现金流区分基本连贯。首轮独立运行 **41 项测试全部通过**，随后以反例发现公开金额上下文和会话日期一致性两处问题。执行作者修复后，本审查者独立重跑 **43 项测试全部通过**，原始反例均得到正确处理，两项确认关闭。下文保留发现与修复证据，避免只写最终绿色结果。

结论只适用于文档声明的单 CNY、已规范化并排序的事件参考；真实交易所/券商、数据库事务与分布式接入仍需各自集成验收。

## 1. 已核对的经济和状态行为

| 内容 | 冷审判断 | 证据与限制 |
|---|---|---|
| 现金形态与复用 | settled、交易应收、交易应付是互斥科目；cash_available 是政策投影，不是额外资产 | 交收将应收/应付变成结算现金，不增加净值；allow reusable 的变化影响可用性而非财富 |
| 现金与库存预留 | 两个策略不能同时消费同一份可用余额或可卖库存 | 预留不记为损益；部分成交释放对应部分，余量继续保留 |
| 成本与做 T | 加权毛价成本与费用分离，总净值桥接合理 | B03 保留未回补导致的少持仓损失；B08 允许用旧可卖库存，但成本仍按声明的总体加权法分配 |
| 收益与外部流量 | 分红应收确认一次，到账不再记收入；入金不是投资收益 | TWR 精确流量边界分段示例为 21%，不存在把存款当成收益的问题 |
| 撤单乱序 | 已知累计成交未对齐时拒绝释放余量 | 这要求上游先对账乱序回报；参考不是任意乱序消息处理器，文档已经说明 |
| T+1 与旧库存 | 正常日期序列下，今天买入不增加今天可卖量；卖出旧库存后再买回不会恢复旧可卖额度 | 这项正常路径通过，但日期不一致输入仍有下述可绕过点 |
| 三个入口对账 | 三种传输 harness 得到同一账本摘要与净值 | 这是共用 reducer 的规范事实重放测试，不是三个真实撮合器或已上线券商适配器 |
| 独立校验 | 除共用内核对比外，测试有独立现金加证券市值恒等式 | 该 oracle 不读取 journal/成本分配，因此比只比较同一实现的两份输出更有意义；仍不替代真实行情/费用/数据库集成 |

已读取 10 个 golden 场景的初始状态、事件、期望和对应断言。未将完整费用引擎、融资、多币种、任意成交 bust、真实券商恢复和送转股上市规则列为“已经发现的缺陷”，因为文档明确它们尚未实现，当前参考也没有冒充具备这些功能。

## 2. EX-REVIEW-01：公开可用现金读取受调用方 Decimal 精度影响

**性质：确认缺陷，影响公开读数的一致性。** `apply()` 与 `snapshot()` 创建固定精度上下文，`cash_available()`、`Order.reserved_cash` 等公开计算没有同样的包裹。当前测试只检查了 snapshot，因此漏掉直接调用路径。

复现输入：期初现金 `1000000.03`；预留买单 1 股，限价 `0.01`，费用预算 `0`。

实际运行输出：

```text
正常上下文 cash_available() = 1000000.02
precision=6 cash_available() = 1.00000E+6
precision=6 snapshot()['cash_available'] = 1000000.02
两次 cash_available 数值相等 = False
```

这不是仅格式不同，而是相差 0.02。当前 `apply()` 内部已有固定上下文，因此本次没有证明入账状态本身因此丢钱；问题是公开接口对同一账户给出不同可用资金。若以后资源协调器直接调用该查询，口径差异会扩散。

建议：固定所有公开金额运算的精度与舍入，或把它们明确收敛到一个统一、内部保护的数值服务。增加直接读取 cash_available/reserved_cash/payable 的上下文对抗测试，不能只验证 snapshot。

## 3. EX-REVIEW-02：会话日期与事件时钟不一致可提前释放 T+1 库存

**性质：确认缺陷，影响原型已经承诺的时间与可卖性。** `session.open` 只要求 payload 的 trading_day 大于旧 day；没有验证其 `effective_at` 的交易所本地日期是否已经到达新交易日。`last_effective_at` 在开户后仍为 None，首条事件也可早于开户日期。

实际运行序列：

1. 2026-11-10 10:00:01 预留买单 100 股。
2. 10:00:02 成交，可卖日 `eligible_on=2026-11-11`。
3. 10:00:03 发送 `session.open`，payload 指定 `trading_day=2026-11-11`，但事件时间仍是 11 月 10 日。
4. 10:00:04 预留卖单 100 股，被接受。

输出：

```text
ledger.day = 2026-11-11
effective_at = 2026-11-10 10:00:04+08:00
reserved_sell = 100
```

另一个反例：开户交易日为 2026-11-10，第一条入金事件为 2026-11-09，当前参考同样接受。

建议：有限 CNY A 股原型可以只校验 `effective_at` 转 `Asia/Shanghai` 后的日期与当前 session 一致；session.open 的新 day 必须匹配该事件本地日期，且严格推进。禁止早于开户边界。完整交易日历、例外会话仍然由 CalendarService 提供，不需要为了此修复临时发明节假日规则。

## 4. 本次未确认的边界，不写成确定错误

- `cash_available` 不能天然等于所有券商口径的 `withdrawable`。当前参考提现同时检查结算现金与可用现金；实际账户还需 CashUsePolicy 与渠道可取规则。没有实际渠道与交收规则证据，不能仅凭习惯认定其所有净额交收场景错误。
- 费用调整、税款、分红权利在参考里是已规范化事实；真实税率和费用预算需要独立成本/规则模块。不把缺少税法引擎误报为 reducer 算术漏洞。
- 参考拒绝取消确认后到来的新成交，要求适配层先补齐累计成交；文档已明确这一前提。生产系统必须永存真实回报并恢复，不能把该参考的拒绝直接用于丢弃券商成交。
- TWR 函数接收已分段且没有区间内外部现金流的 NAV；它不是现金流探测器、年化器或 XIRR 实现。现有命名和说明没有混淆这些用途。
