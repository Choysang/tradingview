## 2. 冷审复现的问题（修复前快照）

### R1：精确十进制转换仍可能静默舍入

位置：`normalization.normalize()` 中 `numeric *= Decimal(op['factor'])`。

直接使用已有日线映射，输入金额字符串 `9007199254740993.1234567890123`，因该端点金额单位转换需乘 1000：

| 项目 | 数值 |
|---|---|
| 数学上的精确结果 | `9007199254740993123.4567890123` |
| 实际参考输出 | `9007199254740993123.456789012` |
| 输出资格 | `publishable=True` |

原因：解析为 Decimal 没有经过 float，但随后的算术仍受当前 Decimal context 精度影响。已有“大数无浮点往返”测试不足以证明任意被接受的字符串可以精确变换。

建议：明确映射输入的精度/尺度上限，超限拒绝；或者按输入与缩放因子的有效位数设置局部 context，并对非终止小数除法规定准确可执行的拒绝或舍入政策。金额不应在没有字段质量说明时被悄悄改变。新增测试应校验精确末位与超限行为，而非只测试类型为 Decimal。

### R2：同一个决策截止时间下，旧任务可覆盖较新的资料包

位置：`ReleaseStore.stage()` 与 `publish()` 的发布顺序约束。

实测步骤：

1. 先 stage `old_job`，输入快照标识 `old`。
2. 再 stage `new_job`，输入快照标识 `new`。
3. 两者 `decision_as_of` 都为 `2026-11-10T06:00:00Z`，所需视图均完整。
4. 先 publish `new_job`。
5. 旧任务调用 `publish('old_job', expected_active='new_job')`。
6. 当前 active 被改为 `old_job`，读取结果回到旧快照。

CAS 能检查调用时声明的旧指针，但没有将这个指针绑定到任务开始的计算基线。相同截止时间在补全、修订或模型重算中并不罕见；仅检查时间严格小于不够。

建议：stage 时记录不可变的基准 release 或单调 generation，并把它纳入身份哈希；publish 必须满足该计算基线，CAS 冲突后不能只更新 expected_active 再重试旧计算。生产系统还需按正式输入快照和版本政策判断是否接受同一 cutoff 的重算；不要把模型名或任意字符串字典顺序当成版本优先级。

### R3：推送心跳的未来时钟绕过了已有时钟检查

位置：`SourceHealth.state()` 中 `now - last_push_heartbeat`。

实测：先 `transport_success(100)`，再令 `last_push_heartbeat=1000`，调用 `state(110)`，得到传输 healthy、`poll_due=False`。模块会拒绝未来内容时间，但未来推送心跳没有同等检查。

建议：通过受控心跳方法更新时间并校验，或者在 `state()` 中拒绝未来心跳；不允许未来值长期掩盖真实推送静默。该问题只涉及示例中的时间一致性，不代表已经观察到某个真实提供商有坏时钟。

## 3. 不应扩大声称的能力边界

- `normalize()` 对实时样本允许缺少已解析 `event_time`，并单独标记 `time_quality=missing`。根节点已将输出改名 `normalization_valid`，明确只表示当前字段变换有效；需要市场时间定位的特征/实盘排名仍要在共同发布门槛拒绝。它不能直接等价于“所有实时策略均可使用”。
- `ReleaseStore` 证明完整视图、不可变版本、原子发布和幂等效果。当前 manifest 是自由 JSON 的哈希，本身不证明每项输入均在 `decision_as_of` 前可得、质量达标、所有数据集 READY。生产发布必须调用公共 manifest/可得性验证器。
- `SourceHealth` 是确定性状态示例，不是实际轮询服务。`transport_success` 需要上游先完成响应类型、登录页、字段、分页检查，不能直接绑定任意 HTTP 200。
- `DurableCursor` 假设传入区间已经由适配器证明连续；它不会从真实页内容中自动发现缺号。没有序号的资讯源另用区间与分页对账，不应伪造连续序号保证。

以上边界可以通过清晰契约保留为参考实现的职责划分；不需要把一个小示例扩张成全部生产系统。
