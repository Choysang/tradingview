# 03 · 系统架构与技术栈

> 本卷回答：系统分几层、每层只做什么、模块之间只通过什么联通、跑在哪些进程里、用什么技术以及为什么。
> 每条设计都写明依据：来自审计（01 卷）、调研（09 卷）或本项目实验台账（E 编号）。

## 1. 约束（设计必须服从的事实）

| 约束 | 事实 | 对设计的影响 |
|---|---|---|
| 生产机 | Windows Server 2025，2 核 8 GB，同机还有别的应用；C 盘约 50 GB 可用 | 不能常驻重型服务；进程总内存预算 3.5 GB；一次只跑一个重任务 |
| 计算机 | 本地 Windows 11 PC，常关机，有 CPU 版 torch | 训练、挖掘、批量回测放 PC；PC 不在线时生产链路必须照常 |
| 市场 | 沪深主板为主，只做多，T+1，涨跌停，整手 | 成交规则是一等公民，写进唯一的规则表和撮合器 |
| 数据 | 免费源为主，按 IP 限流、口径各异；盘中与新闻只从 2026-11-02 起有时点正确的记录 | 采集与消费解耦；每条数据自带来源、时间语义和新鲜度 |
| 开发方式 | 一个人加多个编码智能体并行 | 契约先行；包边界即所有权边界；验收测试即规格 |
| 证据 | 台账 92 条实验里，多数想法在真实成交仿真下不成立 | 平台不预设任何策略有效；每个功能都带证据等级并被持续检验 |

## 2. 十二条架构原则

每条后面是它要消除的现状问题。

1. **一个事实只存一处。** 现状有 11 类存储、两个 data 根目录，同一只股票的历史在快照、抽屉、形态雷达、相似情景里来自四套来源（审计 A2、A4）。新系统只有一个数据湖和一个状态库，任何产物都能回答“谁写的、哪个版本、谁在读”。
2. **契约是模块之间唯一的耦合。** 现状有三套互不相通的契约：旧看板契约用 6 位代码和浮点数，新内核契约用 `CN.SH.600000` 和 Decimal，新闻告警直接写裸字典（审计 A4）。新系统只有一个 `contracts` 包，数据表、事件、接口、前端类型全部由它生成。
3. **函数式内核，命令式外壳。** 规则、撮合、账本、指标、统计全部是不做 IO 的纯函数；网络、磁盘、时钟只出现在适配器里。这样内核可以被穷举测试，也能被多个智能体并行改写而互不干扰。
4. **时间是一等公民。** 每一行数据都带“何时发生、何时公开、何时收到、何时可用”。任何决策只能通过 `DataView` 取数，`DataView` 只返回决策时刻已经可用的行。现状只有新闻采用了时间字段，其余是“当前快照冒充历史”（审计 A2）。
5. **未知是一个值，不是 0。** 现状有常数 0.62 冒充自由流通市值、`fill_null(0)`、占位字符串“A股全市场”（审计 A1、A2）。新系统的契约里缺失就是 null，派生指标声明自己依赖哪些输入，输入缺失时输出 null 并写明原因。
6. **一切带版本，只追加。** 事件、策略规格、每日报告、实验记录都不可变；修订是新增一个版本并指向被替代者。现状的 GET 接口会重算并覆盖已推送的当日报告（审计 A4）。
7. **一个撮合器，一本账。** 现状至少有 15 套各自独立的成交与计分逻辑，“持有 5 天”有四种含义（审计 A3）。新系统里选股策略、个股操作策略、大模型、强化学习都只产出意图，成交和记账只发生在一处。
8. **展示给用户的每个结论都带证据等级。** 现状产品把样本内外都不赚钱的战法判成“依赖周期”并让它投票，而台账已判定它们无效（审计 A6）。新系统里“已验证、检验中、未检验、已证伪”是界面上的固定标签（与策略状态的对应见 06 卷第 5 节）。
9. **大模型只出判断，分数由代码算。** 依据：大模型逐日决策的运行间方差大、动作翻转（AlphaForgeBench，09 卷）；泄漏控制后的 A 股评测里 10 个模型有 9 个选股 alpha 为负（KTD-Fin，09 卷）；本项目经验卡同一结论。
10. **响亮地降级。** 现状 `/health` 恒返回 ok，数据冻结两天无人知晓（审计 A1、A5）。新系统里新鲜度贴在数据上，过期的数据带着过期标记流到界面，告警同时发出。
11. **能力只定义一次，三处暴露。** 沿用现有的能力注册表设计：一条能力绑定一个路由函数，REST 清单、MCP 工具、`llms.txt` 都由它生成。
12. **按小机器设计，按接口升级。** 物理层（Parquet 加嵌入式库）藏在端口后面；换成服务型数据库、消息队列、编排器时，表结构和调用方不变。升级触发条件写在第 11 节。

## 3. 分层

```text
                         ┌───────────────────────────────────────────────┐
  contracts（唯一真源）   │ ids · units · time · datasets · events · api   │
  生成：OpenAPI / TS /   │ strategy · trading                             │
  DDL / JSON Schema      └───────────────────────────────────────────────┘
                                         ▲ 所有层只依赖它和下层
 L8 界面      apps/web        推荐榜 · 板块 · 个股工作台 · 策略联赛 · 复盘 · 数据健康
 L7 服务      serve           REST · SSE（主题+版本）· MCP · 能力注册表
 L6 评估      league          统计门槛 · 联赛 · 融合权重 · 前向对账
 L5 交易      sim             组合层 · SimExchange · Ledger（回测 = 纸面 = 实盘同构）
 L4 策略      strategies      选股器 · 操作策略 · 否决器 · 风险叠加（只产出意图）
 L3 信号      features/intel  特征面板 · 四面信号（消息 / 情绪 / 资金 / 技术）· 市场状态
 L2 数据      lake            数据湖（raw / canonical / derived）· 目录与状态库 · DataView · 事件日志
 L1 采集      ingest          每源一个适配器 · 规范化 · 校验 · 健康 · 回补
 L0 外部      行情 · 新闻 · 公告 · 龙虎榜 · 日历 · 社区 · 外盘 · 大模型 API

 横切：kernel（纯函数：日历、规则表、涨跌停、费用、撮合、账本、指标、统计）
       runner（作业图、调度、运行账本、看门狗）
```

依赖方向只能向下。`kernel` 不依赖任何有 IO 的包。任何一层都不能跳过 `lake` 直接访问外部数据源：策略永远读不到“源”，只读得到“数据集”。这就是“策略的实现不会被数据层堵住”的结构保证：采集失败只会让数据集的新鲜度变差，不会让策略代码抛出网络异常。

### 3.1 一次决策的数据流

```text
源 ──采集──▶ raw（原始响应，不可变）──规范化+校验──▶ canonical（规范表）
                                                     │  事件：dataset.updated
                                                     ▼
                                  特征与信号作业 ──▶ derived（特征面板、四面信号、状态）
                                                     │  事件：signals.updated
                                                     ▼
   DataView(decision_time, snapshot_id) ──▶ 选股器 ──▶ 候选 + 分数
                                          操作策略 ──▶ ActionIntent（意图）
                                                     ▼
                              组合层（预算、去重、否决、风险叠加）──▶ OrderPlan
                                                     ▼
                              SimExchange（或实盘通道）──▶ ExecutionReport ──▶ Ledger
                                                     │  事件：ledger.fill / picks.published
                                                     ▼
                              league（到期对账、联赛、权重）──▶ 策略状态变化 ──▶ 回到选股器的权重
```

闭环在最后一步合上：对账结果改变策略的状态和权重，下一个决策日的推荐随之改变。

## 4. 仓库与包边界

新代码放在本仓库的 `rebuild` 分支，分支上的工作树不含任何旧代码；`main` 继续承载线上系统直到切换（理由与备选见 10 卷 D01）。

```text
/
├── AGENTS.md                  一页：命令、边界、禁区、阅读顺序
├── docs/rebuild/              本规格；docs/adr/ 决策记录；docs/archive/ 旧研究与台账（只读）
├── contracts/                 唯一真源（Python 包 pulse_contracts）
│   ├── ids.py units.py time.py        基础类型与单位
│   ├── datasets/              每个数据集一个模型（键、分区、时间语义、新鲜度目标）
│   ├── events/                事件信封与各主题载荷
│   ├── api/                   请求与响应模型
│   ├── strategy/              StrategySpec · Signal · Candidate · ActionIntent
│   ├── trading/               OrderPlan · ExecutionReport · LedgerEntry · PortfolioState
│   ├── workspace/             TradePlan · 自选 · 布局 · 画线 · 笔记 · 告警规则 · 保存的筛选
│   └── gen/                   生成器：OpenAPI、TypeScript、DDL、JSON Schema、字段字典
├── packages/
│   ├── kernel/                纯函数领域内核（无 IO）
│   ├── lake/                  存储端口与适配器、目录、DataView、事件日志
│   ├── ingest/                采集框架 + 每源一个适配器文件
│   ├── features/              特征与四面信号（注册表 + 纯函数）
│   ├── intel/                 消息管线：聚类、实体链接、事件分类、大模型网关
│   ├── strategies/            策略运行时 + 策略库（每个策略一个文件）
│   ├── sim/                   SimExchange · Ledger 服务 · 回放驱动
│   ├── league/                评估、统计门槛、联赛、融合
│   ├── runner/                作业图、调度、运行账本、看门狗
│   └── serve/                 FastAPI · SSE · MCP · 能力注册表
├── apps/
│   ├── collector/ stream/ worker/ api/   四个业务进程的装配入口：只做装配，不含业务逻辑（看门狗的极小入口在 ops/）
│   ├── web/                   React 前端
│   └── cli/                   pulse 命令行
├── lab/                       研究工作台（PC）：挖掘、训练、论文复现；只经 contracts 与 lake 交互
├── tools/migrate/             一次性迁移作业：旧数据、台账、前向记录、冻结打分器清单的导入与对账
├── tests/                     跨包验收：标准用例、跨引擎对账、无前视、契约漂移
└── ops/                       服务定义、部署脚本、作业清单（全部纳入仓库）
```

允许的依赖（箭头指向被依赖方）：

```text
kernel   → contracts
lake     → contracts, kernel
runner   → contracts, lake                      （只提供作业框架，不认识任何业务作业）
ingest   → contracts, kernel, lake
features → contracts, kernel, lake
intel    → contracts, kernel, lake
sim      → contracts, kernel, lake
strategies → contracts, kernel, lake, features  （登记库与运行时；只产出意图）
league   → contracts, kernel, lake, sim, strategies
serve    → contracts, lake 与各业务包的公开查询接口
apps/*   → 任意包（装配入口：把各包的作业注册进 runner，把各包的路由注册进 serve）
lab      → contracts, kernel, lake, features, strategies, sim, league 的公开接口
```

融合权重由 `league` 写成数据表，`strategies` 读表而不导入 `league`，所以两者之间没有循环依赖。这条规则由导入检查在持续集成里强制执行。每个包有自己的 `AGENTS.md`，写明所有权文件清单和公开接口；别的包只能用公开接口。

现状里“生产代码读研究目录的产物”（新闻告警读 `.work/lab/main/sw_industry.parquet`，审计 A2）在这个结构里无法发生：`lab` 的产出必须先登记成数据集，生产代码只认数据集。

## 5. 进程拓扑

### 5.1 服务器（常开，系统的记录方）

| 进程 | 职责 | 内存预算 | 说明 |
|---|---|---|---|
| `pulse-collector` | 全天候采集：行情快照、7×24 电报、公告、日历、社区热度；写 raw 与 canonical；维护源健康 | 0.4 GB | 异步单进程；每个主机一个限速器；不受交易日限制（现状只在交易日 08:00–22:00 录，夜间与周末的消息丢失，审计 A5） |
| `pulse-stream` | 事件驱动的轻任务：消息管线（聚类、确认、实体链接、事件分类、大模型调用）、盘中信号、持仓告警、交易计划重评估 | 0.4 GB | 与重任务队列完全分开，盘中的消息处理不会排在回测后面。延迟目标：一条快讯从收到到规则路径的告警不超过 10 秒，走大模型的不超过 30 秒 |
| `pulse-worker` | 批作业：日更、特征、信号、推荐、纸面撮合、对账、联赛结算 | 峰值 2 GB | 同一时刻只跑一个重任务（沿用台账的排他队列规则） |
| `pulse-api` | 只读为主的服务：REST、SSE、MCP、静态前端 | 0.5 GB | 不持有业务状态；不在请求里访问外部源；嵌入式查询引擎设内存上限 256 MB，快照类查询必须带日期分区条件 |
| `pulse-watchdog` | 心跳监督、进程重启、新鲜度与磁盘水位告警、推送 | 0.05 GB | 极小、无第三方依赖；它挂了由系统服务管理器拉起 |

五个进程合计常驻约 1.9 GB，批作业峰值时约 3.4 GB，在 3.5 GB 的预算内。它们都注册为系统服务，开机自启，定义文件在 `ops/`。现状的计划任务定义只存在于服务器上，仓库里只有文档提及（审计 A4）；新系统里部署即代码。

### 5.2 本地 PC（按需，算力方）

`pulse-lab`：拉取服务器的数据湖快照（按清单增量），在本地跑挖掘、训练、批量回测、论文复现，把结果作为数据集文件推到服务器的收件目录。服务器的 `pulse-worker` 校验后登记入库。PC 从不直接写服务器的状态库。

依据：现状约定“服务器是真实仓库的唯一写入方”（项目记忆），并且 PC 常关机。生产链路的每一步都必须在服务器上独立完成；需要 torch 的打分若进入生产，必须先导出成服务器能执行的形式（线性权重、树模型文件或预计算分数表）。

两个过渡期例外，都有明确的结束条件：

1. **冻结融合分**在移植完成前继续由 PC 上的旧流程产出，作为外部打分表登记入库（06 卷附录 A.1、08 卷 M5）。
2. **约 4,300 个因子的月度信息系数重算**放在 PC 的 `lab` 里跑，结果作为数据集推回服务器；服务器只做融合所需的那几十个因子的每日增量计算。

### 5.3 为什么不是微服务、容器、消息队列

- 2 核 8 GB 上，常驻的编排器、消息队列、服务型数据库各自要占几百 MB 到几 GB，而现有 Pulse 单进程已用约 2.7 GB（服务器实测，项目记忆）。
- Docker Desktop 不支持 Windows Server；Linux 容器需要虚拟机（09 卷，二手来源，未核官方文档）。
- 事件量级是每秒几十条以内，瓶颈从来不是吞吐，而是一致性与可追溯。

## 6. 内部消息接口（模块联通的唯一通道）

### 6.1 事件日志

所有模块之间的通知只走一张表：状态库里的 `event_log`。

```text
event_log(seq 自增主键, event_id, topic, key, version, payload_json 或 payload_ref,
          event_time, available_at, produced_at, producer, trace_id)
consumer_offset(consumer, topic, seq)
```

- **写入方式（发件箱模式）**：改状态和发事件在同一个数据库事务里完成。不会出现“数据写了但事件没发”或“事件发了但数据没写”。
- **投递语义**：至少一次。消费者按 `event_id` 幂等处理，并自己保存消费位置。
- **跨进程唤醒**：消费者每 0.5–1 秒查询一次新序号。同一进程内用内存里的发布订阅即时转发。
- **前端推送**：`pulse-api` 读事件日志，通过 SSE 推 `{topic, key, version}`。前端按主题让对应查询失效并重取。现状的 SSE 只有心跳序号，收盘同步、推荐重算、新闻告警之后已打开的页面不会更新（审计 A4）。

### 6.2 主题清单（第一版）

| 主题 | 键 | 何时产生 | 主要消费者 |
|---|---|---|---|
| `source.health` | 源 ID | 源状态变化（正常、降级、熔断、恢复） | 看门狗、数据健康页 |
| `dataset.updated` | 数据集名 + 分区 | 规范表的一个分区登记入库 | 特征作业、缓存失效、前端 |
| `market.snapshot` | 交易日 | 一帧盘中快照就绪 | 盘中信号、持仓监控、前端 |
| `intel.item` | 消息 ID | 一条消息规范化入库 | 聚类 |
| `intel.cluster` | 事件簇 ID | 事件簇新建或确认等级变化 | 事件分类、告警 |
| `intel.event` | 事件 ID | 结构化事件产出（含标的映射） | 信号、持仓告警、个股页 |
| `signals.updated` | 信号面 + 交易日 | 一批信号写入 | 策略运行时 |
| `picks.published` | 交易日 + 榜单 | 推荐榜发布（不可变版本） | 前端、推送、纸面账户 |
| `sector.heat` | 板块 ID | 升温预选池触发（附冻结的候选名单） | 前端、对账作业 |
| `plan.updated` | 计划 ID | 交易计划生成新版本或失效 | 前端、告警、纸面账户 |
| `workspace.updated` | 用户 + 对象类型 | 工作区对象被写入（多窗口、多设备同步） | 前端 |
| `alert.raised` | 告警 ID | 持仓或观察池告警 | 推送、前端 |
| `order.*` / `ledger.fill` | 账户 + 订单 | 订单状态迁移、成交入账 | 组合页、对账 |
| `strategy.status` | 策略 ID | 生命周期状态迁移 | 推荐权重、联赛页 |
| `league.round` | 赛季 + 轮次 | 一轮结算完成 | 联赛页、权重更新 |
| `job.run` | 作业 + 分区 | 作业开始、成功、失败 | 看门狗、运维页 |

### 6.3 为什么用数据库表而不是消息队列

单机、每秒几十条事件以内时，最需要的是三件事：与状态的原子性、可审计、可重放。数据库表全部满足，而且不引入新进程。升级到 NATS JetStream 的触发条件见第 11 节；因为生产者和消费者只依赖 `lake.events` 的发布与订阅接口，替换不影响业务代码。

## 7. 作业系统（runner）

现状的任务靠时间错开来保证先后（“16:20 的分钟线在 15:35 日更之后”），一个任务失败后下游照常拿旧产物继续跑并重复推送（审计 A1、A4）。新系统按产物依赖编排。

- **作业声明**：每个作业写明输入数据集、输出数据集、触发方式（时间、事件、手动）、分区键、资源等级（轻、重）。作业图由声明推导，不手写先后顺序。
- **就绪判定**：下游只在上游输出分区“已登记且通过质量闸门”时才运行。上游失败时下游短路，并记录“因何未运行”。
- **幂等**：一次运行的身份是（作业、分区、输入快照）。同样的输入重跑得到同样的输出版本，不重复产生副作用。推送按（主题、键、版本）去重。
- **互斥**：跨进程文件锁加运行账本。重任务全局串行。
- **回补**：缺口检测发现缺分区时生成回补任务；回补与日常运行走同一段代码。
- **质量闸门**：覆盖率闸门是日更的硬性收尾步骤（低于 95% 拒绝产出推荐，95–98% 标记降级；现状这个闸门只在 PC 上跑，审计 A5）。
- **运行账本**：`job_run(job, partition, input_snapshot, status, started_at, finished_at, attempts, error, output_versions)`，运维页和 `/health` 直接读它。
- **时钟与日历**：全系统只有一个时钟服务和一个交易日历数据集。日历缺失时显式告警并拒绝运行依赖日历的作业，不退回“只看工作日”的规则（现状静默回退，审计 A2）。

不引入 Dagster 等编排器的理由：它们需要常驻服务和元数据库，在这台机器上代价高于收益。作业声明的字段与资产化编排器的概念一一对应，将来迁移是机械的。

## 8. DataView 与快照

- **目录即版本**：数据湖的每次写入都在目录里登记一个新快照号（单调递增）。`snapshot_id` 唯一确定“当时湖里有哪些文件”。
- **DataView**：由（`decision_time`、`snapshot_id`、知识模式、规则集版本、股票池）确定。取数时自动加上 `available_at <= decision_time`。
- **两种知识模式**：`AS_OBSERVED` 用我们真实的收到时间（前向运行与盘中回放）；`AS_PUBLISHED` 用可靠的原始发布时间（历史重建）。同一份研究必须声明用的是哪一种。
- **缓存键**：所有研究与评估缓存以（代码版本、`snapshot_id`、参数）为键。现状的缓存键不含文档类元数据，龙虎榜空日更新后面板缓存不失效（审计 A2）。
- **无前视测试**：对每个特征、信号、策略自动执行“把数据截断到任意一天后重算，结果必须与全量一致”。这是从现有 `test_playbook_library` 继承的做法，新系统把它推广为所有注册对象的默认测试。

## 9. 技术栈

版本一律取实现当天的最新稳定版并锁进锁文件。调研得到的版本号多数未经二次核实，列在 09 卷，不写进本表。

| 层 | 选择 | 理由 | 升级路径 |
|---|---|---|---|
| 语言与工具 | Python 3.14，uv 工作区，Ruff，Pyright | 现有资产与生态都在 Python；uv 工作区天然对应包边界 | — |
| 列式计算 | Polars（惰性与流式） | 旧架构文档自述：750 日 × 5000 只、2 万个信号的组合回测约 1.5 秒；注意经验卡“join 后先排序再做窗口计算” | 热点函数用 Rust 插件重写 |
| 分析存储 | Parquet 数据湖 + 自建目录（清单表）；DuckDB 只读查询 | 数据量小（全 A 日线 3 年约 400 万行；快照每个交易日约 60 MB，一年约 15 GB）；追加不可变文件天然适合多读者单写者 | DuckLake（概念与自建目录一一对应）；再往后才是服务型数据库 |
| 状态存储 | SQLite（WAL），一个文件 | 目录、事件、账本、策略登记、工作台状态需要事务；写入频率低；与事件发件箱同库可保证原子性 | PostgreSQL（表结构由契约生成，换驱动即可） |
| 契约 | Pydantic v2 模型 → OpenAPI → TypeScript 客户端；数据集模型 → DDL 与校验器 | 一处定义，四处生成；漂移检查进持续集成 | 需要多语言时换 TypeSpec 或 Protobuf |
| 数据校验 | 基于 Polars 的声明式校验库（Pandera 或 dataframely 二选一，在 M0 用同一组规则各实现一次后定） | 校验规则与数据集模型同源 | — |
| 服务 | FastAPI，SSE，官方 MCP SDK | 沿用现状已验证的组合 | — |
| 前端 | React 19，Vite，TanStack Router 与 Query，轻量状态库 | 服务端状态交给 Query，由 SSE 主题驱动失效；本地状态极少 | 需要离线与多端同步时评估同步引擎 |
| 图表 | lightweight-charts v5 主图与副图（Apache-2.0，需保留署名）；ECharts 做热力图与统计图 | v5 支持多窗格与插件；指标、画线、回放自研（见 02 卷） | — |
| 大模型 | 统一网关：结构化输出校验、调用账本、预算熔断、提示词版本化；供应商可替换 | 现状已有调用台账与截止时间的好做法，推广为唯一入口 | — |
| 服务化 | Windows 服务包装器（WinSW 或 NSSM，M0 选定）+ 看门狗 | 开机自启、崩溃重启 | — |

不采用：服务型列存（ClickHouse、StarRocks 等）、时序数据库、Kafka 类消息系统、工作流引擎、容器、特征平台、SSR 框架。理由统一：常驻资源与运维成本高于它们在这个量级上的收益。

## 10. 统一的缺失、新鲜度与错误模型

- **Provenance 贴在数据上**：每帧、每个分区、每个报告都带 `source`、`data_as_of`（数据自身的时刻）、`produced_at`（处理时刻）、`trade_date`、`freshness`（fresh、stale、expired）、`quality`（ok、degraded、refused）、`missing_fields`。现状把处理时刻当数据时刻，周末抓回周五的快照会显示“就绪、交易日为周六”（审计 A1）。
- **新鲜度由一个函数判定**：输入是数据集的新鲜度目标和交易日历，输出三态。`/health`、数据健康页、界面角标都调用它。
- **错误通道唯一**：适配器把外部错误归为四类：被拒（403、WAF、跳转）、超时、格式变化、空结果。四类对应固定的处置：被拒立即停并进入长冷却；超时短冷却后探测；格式变化隔离原始响应并告警；空结果按源的语义判断是否算失败。业务代码里不允许裸 `except`。
- **派生指标声明输入**：例如“晋级率”声明依赖“昨日涨停名单”。输入缺失时输出 null 和原因，而不是用别的东西凑（现状在实时模式下晋级率恒近 100%，审计 A1）。

## 11. 何时升级物理层

| 触发条件（可观测） | 动作 |
|---|---|
| 状态库写锁等待重试持续超过每分钟 30 次，或需要远程多机访问 | 状态库换 PostgreSQL |
| 数据湖出现多写者，或小文件数超过 5 万且压缩跟不上 | 目录换 DuckLake |
| 事件需要跨机投递，或单主题持续超过每秒 500 条 | 事件日志换 NATS JetStream |
| 作业数超过 80 个，或需要多机执行 | 作业系统换资产化编排器 |
| 单次全市场打分超过 60 秒且剖析显示瓶颈在 Python | 热点改 Rust（Polars 插件或 PyO3） |

在此之前升级没有收益。现状的问题不是数据库性能，而是没有统一的数据模型（04 卷）。

## 12. 安全与预算

- 写操作接口（模式切换、同步触发、策略状态变更、工作台写入）必须鉴权；默认只监听回环地址，经隧道访问。现状的管理接口无鉴权（审计 A1 末尾）。
- 密钥只放在访问受限的密钥目录，由网关读取；不进仓库、不进日志、不进错误信息（现状有一处把响应正文带进错误信息，审计 A5）。
- 外部请求预算按主机设全局令牌桶（跨进程）；大模型按日设调用次数与费用上限，超限熔断。
- MCP 只暴露登记为只读或显式标记为写入的能力；会产生写入的 GET 不允许存在。

## 13. 扩展方式（加东西只动一处）

| 要加的东西 | 做法 |
|---|---|
| 数据源 | `ingest/sources/` 加一个适配器文件：声明源等级、限速、字段映射、单位换算；附录制的原始样本作测试 |
| 数据集 | `contracts/datasets/` 加一个模型；生成 DDL、校验器、字段字典 |
| 特征或信号 | `features/` 加一个注册函数：声明输入列、输出列、时间语义；无前视测试自动覆盖 |
| 选股策略或操作策略 | `strategies/library/` 加一个文件：`StrategySpec` 加纯函数；自动进入联赛的最低一级 |
| 事件类型 | `contracts/events/` 加载荷模型；主题清单加一行 |
| 接口能力 | 在能力注册表登记一个路由函数；REST 清单、MCP、`llms.txt` 自动同步 |
| 页面 | `apps/web` 的视图注册表加一行，加一个功能目录 |
